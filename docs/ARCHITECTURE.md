# 코드 및 발표 자료 분석

## 최종 구현의 모듈

최종 버전 소스는 [`src/`](../src/)에 있습니다.

| 파일 | 책임 |
| --- | --- |
| `client.c` | 접속, 키 교환, 메뉴, 업로드·다운로드, 파일 목록 및 수신 검증 |
| `server.c` | 접속 수락, `fork()`, 클라이언트 식별, 파일 저장·전송, 암호화된 목록 |
| `eddsa.c` | PEM 키 로드 및 EVP 기반 Ed25519 서명·검증 |
| `aes.c` | AES-256-GCM 초기화, AAD, 스트리밍 암복호화 및 태그 처리 |
| `x25519.c` | 임시 X25519 키 생성, 공유 비밀값 계산, HKDF-SHA256 |

## 인증과 키 관리

서버와 클라이언트는 장기 Ed25519 키를 보유합니다. 핸드셰이크는 양쪽 임시 X25519 공개키와 역할 구분 문자열(`X25519-SERVER`, `X25519-CLIENT`)을 서명합니다. 서버는 등록 공개키로 클라이언트 서명을 확인하고 일치하는 파일명을 신원으로 사용합니다.

X25519 자체는 인증 알고리즘이 아닙니다. 인증은 Ed25519 서명 및 사전 신뢰한 공개키로 수행합니다. X25519 공유 비밀값은 양쪽 임시 공개키를 salt로 하는 HKDF-SHA256에 입력되어 AES 세션키가 됩니다.

## 파일 처리

송신 측은 파일의 SHA-256을 계산하고 `Signed_Info`(파일명, 크기, 해시)를 서명합니다. 같은 구조체가 AES-GCM의 AAD로 사용됩니다. 파일 본문은 65,536바이트씩 처리합니다. 수신 측은 PID를 포함한 임시 파일에 기록하고 태그 검증, 해시 비교, Ed25519 검증 후 `rename()`으로 최종 경로에 반영합니다.

서버 파일 목록은 개수와 IV를 담은 헤더를 AAD로 사용하고 목록 항목을 암호화합니다. 파일 목록에는 별도 Ed25519 서명이 없으며 인증된 세션에서 GCM 태그로 검증합니다.

## 단계별 변화와 발표 자료의 관계

1~4단계는 [`history/01-socket`](../history/01-socket/) ~ [`history/04-eddsa-aes`](../history/04-eddsa-aes/), 5단계는 [`src/`](../src/)에 해당합니다.

- 1단계는 TCP 메시지 통신, 2단계는 기본 파일 전송을 구현합니다. 서버 포트는 1단계가 10101, 2단계가 12345입니다.
- 3단계는 파일명·크기·해시에 대한 Ed25519 서명을 사용합니다.
- 4단계는 사전 공유 `aes_key.bin`(또는 `AES_KEY_FILE`)과 AES-GCM을 사용합니다. 서명 입력은 파일 전체와 해시를 결합하므로 파일 크기에 따른 메모리 할당이 발생합니다.
- 5단계는 메타데이터·해시 서명과 스트리밍 처리, 접속별 세션키, 상호 인증, 다중 접속, 메뉴 및 암호화된 목록을 구현합니다.
- [최종 발표 자료](presentations/04-final-2026-10-12.pdf) 8~15쪽은 이 최종 구조와 대응합니다. [9월 발표 자료](presentations/03-semester2-2026-09-07.pdf)의 사전 공유 AES 키 및 파일 전체 서명 설명은 4단계에 해당하므로 최종 실행 안내와 혼용하지 않습니다.
- 최종 발표 자료의 ‘파일 해시에 서명’은 요약 표현입니다. 실제 서명 입력에는 파일명과 크기도 포함됩니다.
- 발표 자료의 PID별 임시 파일 설명은 임시 경로 충돌을 줄이는 방식입니다. 동일한 최종 파일명으로 동시 업로드하면 마지막으로 성공한 `rename()` 결과가 남습니다.

## 구현의 한계

- 구조체를 네트워크에 그대로 보내므로 크기 정적 검사만으로 서로 다른 엔디언·ABI 간 호환성을 보장하지 않습니다. 정식 직렬화 형식은 없습니다.
- 명령, 파일명, 파일 크기, 해시 등 일부 메타데이터는 평문입니다. 전체 TCP 채널을 암호화하는 TLS 구현이 아닙니다.
- 파일별 접근 권한, 저장 용량 제한, 접속 시간 제한 및 세션 내 메시지 순서·재전송 방지 정책이 없습니다.
- `fork()`로 접속을 처리하지만 동시 접속 수를 제한하는 별도 정책은 없습니다.
- 인증 전 복호화된 데이터가 임시 파일에 기록됩니다. 성공 전에는 최종 파일명으로 확정하지 않습니다.
- 초기 개발 단계는 학습 기록이며 최종 단계와 동일한 보안 기능을 제공하지 않습니다.

이 분석은 제공된 코드와 발표 자료 텍스트를 비교한 결과이며 별도 보안 감사 또는 상용 서비스 적합성 인증이 아닙니다.
